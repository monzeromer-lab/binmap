## 1. Summary

Binmap is a desktop application that understands a Rust program at both the source level
and the machine level at the same time, and uses that dual view to answer three questions
developers currently answer by hand:

1. **Why is this wrong?** — root cause analysis on crashes and misbehaviour in optimized builds.
2. **Why is this slow?** — performance attribution from machine events back to source constructs.
3. **Why is this so big?** — binary size attribution, and what to change to shrink it.

It is a deterministic analysis engine with an optional language-model layer on top. The
engine measures, symbolizes, and verifies. The model explains, hypothesizes, and proposes.
Every claim a model makes is displayed alongside the tool output that supports it.

**It is a GUI application.** There is no command-line product surface. The reasoning is in §5,
non-goal N8.

---

## 2. Problem statement

Rust developers hit a wall the moment they leave debug builds.

**The source-binary gap.** In a release build, variables are "optimized out," functions are
inlined into unrecognizable shapes, and stepping through source lies about what actually
executed. The existing answer is to drop into raw disassembly, which most application
developers cannot read fluently and which no tool connects back to their source.

**Size is unattributed.** `cargo-bloat` and `bloaty` will tell you that a symbol costs 40 KB.
Neither can tell you that it costs 40 KB because a generic function was monomorphized into
twelve near-identical copies, nor what to restructure to collapse them. The measurement tools
stop exactly where the useful advice would start.

**Performance data is a wall of samples.** `perf` and flamegraphs show where cycles go.
Turning "this symbol is hot" into "this is hot because the compiler could not vectorize the
loop, because of this aliasing assumption in your source" is expert work that does not scale.

**Configuration is folklore.** That `panic = "abort"` deletes unwinding tables, that
`codegen-units = 1` interacts with LTO, that `opt-level = "z"` sometimes produces *slower and
larger* output than `"s"` on a given crate — this lives in blog posts and tribal memory rather
than in a tool that measures it on your actual code.

Underneath all four is one gap: **no tool holds the source and the binary in view
simultaneously and reasons across the boundary.** Debuggers see the binary. Linters see the
source. Profilers see samples. Nothing bridges them.

**And none of this is legible as text.** A treemap of a binary, a flamegraph with inline frames
expanded, a source pane whose selected line lights up four scattered instruction blocks — these
are the product. That is the case for building a GUI rather than a CLI with a GUI bolted on.

## 3. Why now

- **`gimli`, `object`, and `addr2line` are mature.** Reading DWARF from Rust is a library call
  rather than a research project.
- **Rust desktop UI became viable.** GPUI plus `gpui-component` ships a virtualized table for
  hundreds of thousands of rows, a code editor stable at 200K lines, and a dock layout. Those
  are three of the four hardest views in this product, and eighteen months ago they did not
  exist in Rust.
- **Agent interoperability standardized.** ACP means supporting one protocol grants access to
  Claude Code, Codex, Gemini CLI, Copilot, Goose, Kimi CLI and a growing registry of others,
  rather than building an integration per agent.
- **Language models are good at exactly this bridge.** Mapping between two representations of
  the same artifact is a translation task. They are unreliable at arithmetic over addresses,
  which is why the engine, not the model, computes facts.
- **Rust's size problem is economically material.** WASM payloads, embedded targets, and
  container images all make binary bytes a line item.
- **The closest thing to a competitor is closed.** Pernosco proves demand for intelligent
  replay debugging. It is a paid hosted service. There is no open, local equivalent.

## 4. Users

### Persona A — Embedded / WASM developer ("bytes are budget")
Ships to a device with 256 KB of flash, or a WASM bundle where every kilobyte is latency.
Maintains a hand-tuned `Cargo.toml` copied from `min-sized-rust` and periodically runs
`cargo-bloat` and squints.
**Wants:** a number that goes down, with proof nothing broke.
**Primary surface:** Size Explorer, Profile Lab.

### Persona B — Systems developer debugging a release build ("it only crashes in prod")
Has a core dump from a stripped or lightly-stripped release binary, a stack trace with inlined
frames, and no ability to reproduce locally.
**Wants:** the faulting line, the values that led there, and a hypothesis.
**Primary surface:** Crash Analysis.

### Persona C — Crate maintainer under performance pressure ("a regression landed")
Owns a widely-used crate. A benchmark regressed 12% and bisect points at a 400-line refactor.
**Wants:** attribution of the regression to a specific construct, and a verified fix.
**Primary surface:** Flamegraph, Profile Lab diff mode.

### Explicit non-users (v1)
- **The reverse engineer with no source.** Binmap's thesis is the source-binary bridge;
  without source it degrades to a worse Ghidra.
- **The CI pipeline.** A GUI-only product cannot serve automated builds. This is a real cost,
  acknowledged in §5 N8 and §13 R13.

## 5. Goals and non-goals

### Goals
- G1. Reduce binary size on a real crate by a measurable amount with automatic verification
  that tests still pass. **This is the v1 headline.**
- G2. Attribute size, cycles, and crashes to *source constructs*, not just symbols.
- G3. Remain fully functional with the model layer disabled.
- G4. Never present a model claim without its supporting evidence visible.
- G5. Run entirely on the user's machine by default. Nothing leaves the host unless the user
  explicitly selects a cloud reasoner.
- G6. Support both external agents (ACP) and direct API access, with the user's existing tools
  and subscriptions rather than a new one.
- G7. Ship something useful every 8-12 weeks.

### Non-goals (v1)
Recording these matters more than recording the goals; a solo project dies from scope creep.

- **N1. Not an IDE.** No editing, no LSP, no build-on-save. It reads your code; you edit
  elsewhere.
- **N2. Not a source-only linter.** If Clippy can find it, Binmap should not try.
- **N3. Not cross-platform in v1.** Linux x86-64 only. `rr` is Linux-x86-64-only and that
  constraint propagates.
- **N4. Not a replacement for GDB/LLDB.** No general-purpose interactive stepping UI.
  Binmap drives debuggers; it is not one.
- **N5. Not a hosted service.** No accounts, no server, no telemetry.
- **N6. Not C/C++ in v1.** The architecture must not *preclude* it, but no effort is spent.
- **N7. No autonomous commits** without the trust tier explicitly raised, never as default.
- **N8. Not a command-line tool.** There is no shipped CLI and no CI mode. The engine remains a
  library and a **development-only headless harness** exists to drive the eval suite, but it is
  not packaged, documented, or supported as a user surface. The product is one GUI binary.
- **N9. Not an agent host.** Binmap connects to agents; it does not implement one. External
  agents own their authentication, billing, and reasoning.

## 6. Product principles

**P1 — Deterministic core, optional intelligence.**
Every feature must produce value with the model turned off. "No reasoner" is a first-class
selectable option, not a hidden flag. The model adds explanation, ranking, and proposal; it
never adds facts. A bad model output degrades the product; it cannot break it.

**P2 — Evidence or it didn't happen.**
Every finding carries a chain of evidence, each item tagged with its provenance. The UI renders
these differently and always visibly. A user must never have to guess whether they are reading
a measurement or a guess.

**P3 — The verifier is the product.**
The ability to *prove* a change is safe and beneficial is worth more than the ability to
propose it. Build the verifier first; proposals are cheap once verification exists.

**P4 — Local by default.**
Binaries are proprietary. The default reasoner is local or none. Cloud access is explicit,
visible, and disableable at the project level.

**P5 — Trust is a dial, not a mode.**
The four tiers (§7) are one mechanism at four settings, always visible, never silently raised.

**P6 — Bring your own reasoner.**
Users have existing agent subscriptions and API keys. Binmap adapts to them rather than
requiring a new account. Supporting ACP means supporting an ecosystem, not a vendor.

## 7. The trust ladder

| Tier | Behaviour | Gate |
|---|---|---|
| 0 · Observe | Measures, ranks, explains. Read-only. | — |
| 1 · Propose | Generates diffs. Never applies them. | Human review |
| 2 · Tune | Modifies build configuration only. | Tests pass + significant benchmark win |
| 3 · Autonomous | Applies source patches, verifies, opens a PR. | All of Tier 2 + sanitizers clean + explicit opt-in |

**Default is Tier 1.** Tier 3 requires a config file change, not a UI toggle.

**Ship order is 0 → 2 → 1 → 3.** Build configuration is semantically safe, trivially
reversible, and produces the most dramatic early wins.

The tier also governs what an external agent may do: it filters the tool list exposed over MCP
and drives the response to ACP permission requests. See `DESIGN-AI.md` §9.3.

## 8. Requirements by phase

Each phase ships a usable application. Estimates assume ~30 hours/week, solo, with a learning
curve on binary tooling **and on GPUI**. They are longer than the v0.1 estimates because every
phase now carries its own UI work rather than deferring it behind a CLI.

## 9. The verification harness (cross-cutting)

Shared by every phase, built in Phase 0. Any proposed change — configuration or source, from a
native loop or an external agent — must pass:

1. **Build** succeeds, warnings diffed against baseline.
2. **Test suite** passes.
3. **Benchmark**, if declared, shows a statistically significant improvement or no significant
   regression. Significance properly computed, not single-run comparison.
4. **Sanitizers** when `unsafe` is touched: Miri where applicable, ASan/UBSan otherwise.
5. **Size** measured and recorded regardless of objective.

Rejected candidates are shown in the UI with the failing gate named, never silently dropped.

**The verifier sits downstream of every permission grant.** An agent authorised to edit source
still cannot land a change that fails a gate.

## 12. Success metrics

### Adoption
- 12 months: 1,500 GitHub stars, 10 external contributors
- Packaging: AUR and Nixpkgs entries; a published AppImage or equivalent
- Cited in at least one conference talk or widely-shared blog post

### Product quality (reference corpus, tracked per release)
- Phase 0: median size reduction versus default release ≥25%
- Phase 1: top-3 accuracy on size-driver identification ≥80%
- Phase 2: root-cause top-3 accuracy ≥70%; frame symbolization ≥95%
- Phase 4: root-cause located within budget ≥60%

### Trust (the metrics that determine survival)
- High-confidence findings that are wrong: **<5%**
- Findings with ≥1 deterministic evidence item: **100%**, enforced in code
- ACP finding-gate rejection rate: **<20%** — a higher rate means tool descriptions are failing

## 13. Risks

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| R1 | **Scope explosion.** Debugger, optimizer, GUI, and two AI integration modes, solo. | Critical | Phase gates. Nothing from phase N+1 starts until phase N ships. §5 non-goals are binding. |
| R2 | **Model confabulation about binaries.** | Critical | P1 and P2. Engine computes facts; findings must cite issued evidence. Enforced at the gate (`DESIGN-AI.md` §5.2). |
| R3 | **AI backlash in the Rust community.** | High | Deterministic tool with an optional layer. "No reasoner" is a listed choice, not a hidden flag. Never market as "AI debugger." |
| R4 | **GUI is now on the critical path from week one**, and is a discipline the maintainer lacks. Removing the CLI removed the fallback that used to protect against this. | **Critical** | The two-day GPUI spike (`DESIGN-GUI.md` appendix) becomes **mandatory before Phase 0 begins**, not optional. The engine stays a library with a headless dev harness, so engine work never blocks on UI work. |
| R5 | **DWARF learning curve** stalls Phase 2. | High | Phase ordering puts it third, after two shipped releases. |
| R6 | **Solo maintainer burnout / bus factor 1.** | High | Ruthless phase scoping; public roadmap; good-first-issues from day one. |
| R7 | **Benchmark noise** produces false wins. | Medium | Proper statistics, measured noise floor, interleaved run order. |
| R8 | **Local models too weak; cloud models unusable on proprietary binaries.** | Medium | Prompts authored against weak models. Tiers 0 and 2 need no model. ACP lets users bring an agent they already trust. |
| R9 | **`rr` platform lock.** | Medium | Accepted. Phases 0-3 do not require it. |
| R10 | **Upstream tool churn.** | Low | Version-pin, parse defensively, snapshot tests. |
| R11 | **GPUI is pre-1.0 with a forked ecosystem.** | High | Pin exact versions; isolate in `binmap-gui`; one scheduled upgrade per phase (`DESIGN-GUI.md` §7). |
| R12 | **ACP protocol churn.** Young and versioned; agents vary in conformance. | Medium | Pin and negotiate at `initialize`. Mode A ships first and works standalone, so ACP breakage degrades rather than blocks. |
| R13 | **No CI story.** `binmap ci` was the cheapest path into an organisation's repo. Removing it removes the main non-GUI adoption channel. | Medium | Accepted for v1. The engine remains a library, so a separate CI crate can be published later without redesign. Revisit after Phase 2. |
| R14 | **External agent unpredictability.** Codex and Claude Code have their own loops, contexts, and failure modes, none of which Binmap controls. | Medium | The finding gate treats all external output as untrusted. Rejection rate is a tracked metric. Mode A remains the reference implementation. |

## 14. Open questions

1. **Does the GUI-only decision survive contact with Phase 2?** Crash analysis from a core dump
   is the use case most likely to originate in a terminal. Revisit whether a minimal
   `binmap analyze <core>` launcher that opens the GUI on that core is warranted — that is a
   launcher, not a CLI product, and may be an acceptable narrowing of N8.
2. **Do ACP agents cope with a large domain-specific tool set** they have never encountered?
   Their training is oriented to file editing and shell commands.
3. **Local model floor** for useful monomorphization proposals. Determines hardware
   requirements. Answer empirically in Phase 1.
4. **Evaluation corpus provenance.** Injected bugs scale; real bugs are representative. Report
   the two populations separately.
5. **Company or pure community project?** Affects licensing posture and whether a hosted
   trace-sharing service is ever on the table. The license choice made now is permanent.
6. **Should Binmap also ship as an ACP *agent***, so Zed or JetBrains could drive its
   analysis from their own panels? Possibly a better distribution strategy than a standalone
   GUI. Not v1, but do not close the door.
7. **Accessibility.** GPUI's screen-reader story is weaker than the web's. Decide whether this
   is an accepted v1 limitation and state it publicly.

## Appendix A — Reference corpus

Five crates, fixed at project start, benchmarked every release:

1. An embedded/`no_std` crate — the size-constrained case
2. A generics-heavy library — the monomorphization case
3. A CLI application with a deep dependency tree — the realistic-application case
4. A WASM target — the payload case
5. A multi-crate workspace — the build-orchestration case

Baselines recorded before any code is written.

## Appendix B — First 30 days

1. **Run the GPUI spike first** (`DESIGN-GUI.md` appendix). Two days. Dock layout, a
   100,000-row table, 20,000 painted quads with hit testing, one streaming background task. If
   this disappoints, the plan changes — and you want to know now.
2. Choose a name; write the scope statement into the README **before** code.
3. Repository setup: dual license, CI on Linux x86-64, `cargo-deny` including dependency bans.
4. Define `binmap.json` and the `Finding`/`Evidence` model. This is the contract between
   engine, UI, and eval harness.
5. Build the Phase 0 engine with no AI and no UI, driven by the headless dev harness.
6. Then the shell, then the Profile Lab.

The 30-day success condition: the engine finds a large size win on a real crate with tests
passing, proven by the headless harness, with the shell under construction.
